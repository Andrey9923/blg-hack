# Проверка решения по ТЗ

Актуальный аудит выполнен по постановке задачи, описанию данных и критериям
оценки КосмоХакатона 2026. Ниже перечислено, что демонстрируется в сервисе и
где это проверять.

| Область ТЗ | Реализация | Проверка |
| --- | --- | --- |
| Начальные состояния, среда и задания | `model/resource_env.py` валидирует полный формат `cosmo-B-ops-1.0`; четыре сценария загружаются сервером | `GET /api/scenarios`, `tests/test_baseline.py` |
| Энергия, температура, калибровка и SOC | Единая модель перехода в `Environment`; планировщики не дублируют учёт | `tests/test_runtime.py`, `tests/test_baseline.py` |
| Приоритеты, дедлайны, допустимые исполнители и downlink-limit | `BaselinePlanner` и `StrategicPlanner` резервируют спутники, задания и общий канал до выполнения шага | `tests/test_strategic.py` |
| Приоритетная и коммерческая цели | `strategic-v2` поддерживает `priority` и `revenue`; цель можно сменить на границе | `PlannerRuntime.switch_goal()`, web-панель |
| Пошаговое выполнение и остановка | `run_steps()` / `run_until()` исполняют только фактический префикс | `POST /api/runs/{id}/advance` |
| Новые заявки, отказ и закрытие downlink | Атомарный `apply_event()` принимает сообщения строго на текущем `at_step` | `POST /api/runs/{id}/events`, `tests/test_runtime.py` |
| Настройка эксперимента до старта | Web API применяет заряд, солнечный коэффициент, приоритет и известный outage к копии сценария; изменённый сценарий попадает в result | блок «Экспериментальные условия» |
| Сравнение из одного состояния | `POST /api/runs/{id}/compare` создаёт две независимые ветви с одинаковым digest контрольной точки | блок «Сравнение продолжений» |
| Объяснимость | `explain_trace()` показывает решение, точную причину, телеметрию и известные на тот момент ограничения | блок «Разбор решения» |
| Анализ эффективности | summary, загрузка аппаратов, история, журнал, график средней энергии/температуры, просрочки и выручка | web-панель |
| Машиночитаемый результат и replay | `Session.result()`, runtime history, trace и `replay_episode()` сохраняют и повторяют фактическую историю | `scripts/demo.py`, `tests/test_demo.py` |
| Хранение и доступ | SQLite, восстановление через replay, роли и изоляция владельцев, конфликты ревизий | `tests/test_persistence.py` |
| Выбор ветви | Принятие прямого потомка с проверкой неизменности родителя | `POST /api/runs/{id}/adopt`, `tests/test_persistence.py` |
| Произвольный сценарий и timeline | JSON file picker с валидацией, все задания с пагинацией, все аппараты и шаги с переходом к explain | `web/index.html`, `scripts/ui_smoke.cjs` |
| Воспроизводимость | Python 3.10+, стандартная библиотека, deterministic planner, команды запуска в README | `.github/workflows/tests.yml`, `examples/README.md` |

## Ограничения модели

Орбиты, радиоканалы и телеметрия не рассчитываются: они заданы входными рядами
сценария согласно описанию данных. Web CLI сохраняет запуски в SQLite без
учётных записей и паролей. Расчёты остаются синхронными, изменения в SQLite
сериализуются.
Эвристика strategic является детерминированным rolling-horizon алгоритмом и не
утверждает глобальную оптимальность пропущенного задания.

## Демонстрационный маршрут

1. Запустить `python -m web.app --host 127.0.0.1 --port 8000`.
2. Выбрать `P01_intro`, цель `priority` и нажать «Запустить новую смену».
3. Выполнить несколько шагов, остановиться на границе и принять событие.
4. Запустить сравнение `priority vs revenue`, открыть журнал и объяснить любой
   шаг через пару «шаг + аппарат».
5. Скачать JSON и проверить его командой replay из README.
