# Автономное управление спутниковой группировкой

Детерминированный планировщик для кейса КосмоХакатона 2026. Система назначает
аппаратам ожидание, калибровку, передачу данных (`downlink`) или ретрансляцию
(`relay`), учитывая сроки и приоритеты заданий, энергию, температуру, окна связи,
отказы и общий лимит наземного сегмента. Оператор может остановить смену на
границе шага, передать новое событие, продолжить расчёт из фактического
состояния и сравнить две независимые ветви.

Проект работает на **Python 3.10+ только со стандартной библиотекой**. Внешние
API, серверы баз данных, облачные модели и платные сервисы не нужны.
Веб-сервис сохраняет запуски в SQLite (входит в Python).

## Быстрая проверка для жюри

Все команды выполняются из корня репозитория.

```text
python --version
python scripts/demo.py --output results/demo-result.json
python model/operations.py --result results/demo-result.json --output replays/demo-replay.json
python -m unittest discover -s tests -v
```

`demo.py` использует компактный P01: доходит до контрольной границы, вручную
принимает отказ аппарата, создаёт ветви `priority` и `revenue`, завершает обе,
проверяет точный replay их `summary` и `trace` и печатает сравнение. Файл из
`--output` является обычным `cosmo-B-ops-result-1.0`, поэтому непосредственно
принимается `model/operations.py`. Для суточного P02 запустите:

```text
python scripts/demo.py --scenario P02
```

Подробный набор воспроизводимых команд и ожидаемых проверок находится в
[`examples/README.md`](examples/README.md).

## Архитектура

| Путь | Назначение |
| --- | --- |
| `data/` | Четыре исходных сценария `cosmo-B-ops-1.0` |
| `model/resource_env.py` | Валидация, энергия, температура, допуск и выполнение действий |
| `model/operations.py` | Сессия, события, журнал, summary, export и точный replay |
| `planner/baseline.py` | Простое детерминированное правило для контрольного сравнения |
| `planner/strategic.py` | Основной rolling-horizon планировщик с целями `priority`/`revenue` |
| `planner/runtime.py` | Пошаговое исполнение, остановка, события, switch и fork |
| `planner/analysis.py` | Воспроизводимое сравнение baseline и strategic |
| `planner/cli.py` | Пакетный CLI для расчёта и сравнения |
| `web/` | Локальный операторский HTTP-сервис и браузерный интерфейс |
| `scripts/demo.py` | Короткий сценарий демонстрации и replayable export |
| `tests/` | `unittest`: модель, планировщики, runtime, web, demo и replay |

Модель (`model`) является единственным источником физических и учётных правил.
Планировщики только выбирают команды. `PlannerRuntime` не хранит очередь будущих
событий: событие становится видимо алгоритму только после успешного
`apply_event()` на текущей границе. Все политики детерминированы, случайных seed
и скрытых настроек нет.

## Планировщики и цели

### Baseline

`baseline-v1` является понятной точкой отсчёта. Он сначала калибрует аппараты с
истёкшим допуском, затем сортирует доступные задания по приоритету, запасу до
срока, сроку, стоимости и ID. Для назначения выбирается допустимый аппарат с
наибольшим SOC. Спутник и задание резервируются один раз на шаг, общий лимит
`downlink` соблюдается до передачи команд модели.

```text
python -m planner.cli --scenario data/P01_intro.json --planner baseline --output results/p01-baseline.json
```

### Strategic

`strategic-v2` на каждом шаге оценивает число локально исполнимых окон до срока
каждого задания. Проекция учитывает известные отказы, контакт, калибровку,
энергию, температуру и остаток работы. Алгоритм бережёт единственного будущего
исполнителя, выбирает исполнителя по прогнозному SOC и заранее разрешает
конфликты спутников, заданий и наземного лимита.

Режимы используют одну модель ограничений:

- `priority`: лексикографически защищает задания приоритета 3 и сроки, затем
  учитывает стоимость и ресурсы;
- `revenue`: отдаёт предпочтение рискующим не завершиться заданиям и ожидаемой
  стоимости на оставшийся шаг, не отодвигая срочную критическую работу.

```text
python -m planner.cli --scenario data/P01_intro.json --planner strategic --goal priority --output results/p01-priority.json
python -m planner.cli --scenario data/P01_intro.json --planner strategic --goal revenue --output results/p01-revenue.json
```

Более сложная стратегия не обязана выигрывать на каждом наборе. На P01 режимы
дают те же завершения и выручку, что baseline, хотя ресурсная траектория может
отличаться. На P02/P03 strategic обычно увеличивает пропускную способность; на
P04 цели демонстрируют компромисс между критическими заданиями, общей выручкой
и расходом ресурсов. Отчёт описывает фактический результат жадного алгоритма,
а не доказывает глобальную невыполнимость пропущенных заданий.

## Основной сценарий оператора

Последовательность `create -> advance -> event -> switch/fork -> explain ->
export` доступна через `PlannerRuntime`, HTTP API и браузер.

1. **Create:** выбрать P01-P04, `strategic`/`baseline` и цель.
2. **Advance:** выполнить один или несколько шагов либо остановиться строго перед
   заданным `until_step`.
3. **Event:** передать одно событие, чей `at_step` равен текущему шагу.
4. **Switch/Fork:** сменить цель только для будущих шагов или создать независимую
   ветвь из идентичного фактического состояния.
5. **Explain:** выбрать уже выполненные шаг и аппарат, увидеть запрошенную и
   исполненную операцию, причину, энергию, температуру, калибровку и задание.
6. **Export:** сохранить исходный сценарий, реально полученные события, команды,
   trace, metadata и summary в JSON.

Минимальный программный пример:

```python
from model.resource_env import load
from planner.runtime import PlannerRuntime

run = PlannerRuntime(load("data/P02_shift.json"), goal="priority")
run.run_until(72)
run.apply_event({
    "id": "manual-outage",
    "at_step": 72,
    "type": "satellite_outage",
    "satellite_ids": ["S08", "S10"],
    "end_step": 90,
})
priority = run.fork("priority", goal="priority")
revenue = run.fork("revenue", goal="revenue")
priority.run()
revenue.run()
revenue.export("results/revenue-branch.json")
assert revenue.replay().env.trace == revenue.session.env.trace
```

`switch_goal()` записывает переключение в metadata/history. `fork()` копирует
текущий шаг, энергию, температуру, возраст калибровки, прогресс заданий и
исполненную предысторию; дальнейшие изменения ветвей независимы.

## Веб-сервис

```text
python -m web.app --host 127.0.0.1 --port 8000
```

Откройте <http://127.0.0.1:8000/>. Интерфейс позволяет создать запуск, двигаться
по границам, отправлять JSON-событие, менять цель, делать fork, просматривать
summary/состояния/историю, получать объяснение trace и скачивать result.
Список «Сохранённые запуски» позволяет продолжить смену после перезапуска.
Файл базы по умолчанию — `results/operator.sqlite3`; путь меняется через
`--database`. Все изменения и обе ветви сравнения сохраняются одной транзакцией
до отправки успешного ответа. Runtime восстанавливается из JSON через replay,
без pickle; состояние проверяется по digest. Ограничения в 32 сохранённых
запуска нет. В памяти находятся только запуски текущего запроса.

Операторская панель также позволяет до старта эксперимента изменить начальный
заряд выбранного аппарата, коэффициент солнечной мощности, приоритет задания и
известный интервал недоступности. Кнопка сравнения создаёт две независимые
ветви `priority` и `revenue` из текущей контрольной точки и показывает разницу
по выручке, критическим заданиям, просроченным заданиям и SOC. Интерфейс не
использует сторонние runtime-зависимости: телеметрия, SVG-график и таблицы
строятся браузером из ответа API. Поле загрузки JSON проверяет custom-сценарий
до создания запуска. Таблица заданий имеет страницы по 160 строк; журнал —
страницы по 120 записей с поиском по аппарату, шагу, заданию и причине. Клик
по шагу в журнале открывает объяснение. Старые записи больше не обрезаются.
Timeline показывает все аппараты и любые 48 шагов с переходом к объяснению.
Телеметрия позволяет выбрать среднее, отдельный аппарат или несколько аппаратов
одновременно; задать диапазон шагов и посмотреть значения наведением на точки.
Энергия и температура отображаются отдельно, с физическими единицами и легендами.
Montserrat (кириллица/латиница) и DM Mono включены в `web/assets/fonts` вместе с
лицензиями SIL OFL. Во время работы обращения к CDN не выполняются.

### Редактор будущих операций

Клик по будущей ячейке timeline выбирает аппарат и шаг в редакторе. Можно назначить
ожидание, калибровку или конкретное задание, а также вернуть ячейку планировщику.
Назначенную будущую ячейку можно перенести мышью в свободную ячейку. На телефоне
те же действия доступны через поля редактора. Прошедшие шаги неизменяемы.

Назначения сохраняются в метаданных запуска, переживают перезапуск и наследуются
ветвями. Они заменяют решение алгоритма только для выбранного аппарата/шага;
остальные действия остаются автоматическими. API проверяет структуру, аппарат,
допустимость задания и его временное окно. Энергия, температура и общие ресурсы
проверяются моделью при выполнении: невозможное назначение отображается в trace
как отклонённое, а не обходится. Replay использует фактически записанные команды.

«Прогноз 48 шагов» исполняет копию текущего состояния, не двигая реальную смену.
Полупрозрачные ячейки — прогноз, яркие — ручные назначения. При изменении состояния
прогноз сбрасывается. События, ещё не полученные оператором, прогнозу неизвестны.

«Принять в родительский запуск» сохраняет состояние выбранной ветви под ID
родителя и записывает выбор в историю. Обе ветви остаются доступны отдельно.
Если с момента fork изменились шаг, события, цель или история родителя,
возвращается `409 branch_conflict`: необходимо заново сравнить продолжения.
Интерфейс также передаёт `expected_revision` при изменениях текущего запуска;
устаревшая вкладка получает `409 revision_conflict` и должна открыть запуск снова.

### Учётные записи и несколько операторов

```text
python3 -m web.app --database results/operator.sqlite3 --set-user alice
python3 -m web.app --database results/operator.sqlite3 --auth --host 127.0.0.1 --port 8000
```

Первая команда запрашивает пароль дважды, не записывая его в командную строку.
Минимальная длина — 12 символов; в базе хранится PBKDF2-HMAC-SHA256 с уникальной
солью и 600 000 итераций. В браузере появляется форма входа. Сессия действует
8 часов; токен хранится в sessionStorage вкладки, в БД — только его SHA-256.
Выход и смена пароля отзывают соответствующие сессии.

Роли: `operator` может изменять свои запуски; `viewer` может только читать свои.
`--set-user alice --role viewer` меняет роль существующего владельца и сохраняет
его запуски. Совместного доступа к чужим запускам и административной роли нет.
Чужие ID, включая ветви, export и explain, возвращают 404. Локальные запуски,
созданные без `--auth`, принадлежат отдельному владельцу `local` и автоматически
не передаются новой учётной записи.

SQLite сериализует изменения, включая обращения нескольких процессов к одной
базе; запросы ожидают блокировку до 60 секунд. Длинный расчёт может задержать
другие операции. `RunStore()` остаётся временным хранилищем для тестов и
встраивания; CLI всегда использует `SQLiteRunStore`.

Без `--auth` CLI допускает только loopback-адрес. Для публикации через reverse
proxy включайте `--auth` даже при loopback и используйте HTTPS: см.
[`deploy/README.md`](deploy/README.md).

Основные HTTP-точки:

Все `/api/...` точки также доступны с префиксом `/api/v1/...`. Для браузерных
клиентов CORS можно включить параметром `--cors-origin https://frontend.example`.
По умолчанию внешние origins не разрешены. Preflight поддерживает Authorization
и Content-Type; авторизация и роли одинаково проверяются на обеих версиях пути.
UI использует `/api/v1`. `*` допустим для разработки.

```text
GET  /health
POST /api/auth/login
GET  /api/auth/session
POST /api/auth/logout
GET  /api/scenarios
POST /api/scenarios/prepare
GET  /api/runs
POST /api/runs
GET  /api/runs/{run_id}
POST /api/runs/{run_id}/advance
POST /api/runs/{run_id}/events
POST /api/runs/{run_id}/goal
POST /api/runs/{run_id}/fork
POST /api/runs/{run_id}/compare
POST /api/runs/{run_id}/adopt
POST /api/runs/{run_id}/schedule
POST /api/runs/{run_id}/preview
GET  /api/runs/{run_id}/explain?step=0&satellite_id=S01
GET  /api/runs/{run_id}/result
```

В `POST /api/runs` можно передать встроенный `scenario_id` либо валидированный
объект `scenario`. Ошибки ввода возвращаются как JSON с HTTP 400 и не повреждают
запуск. При `--auth` передавайте `Authorization: Bearer <token>`; токен выдаёт
`POST /api/auth/login` с `username` и `password`. `/adopt` принимает `branch_id`.
Коды ошибок: 400 — неверный ввод, 401 — требуется вход, 403 — запрет записи,
404 — объект недоступен, 409 — конфликт ревизии или выбора ветви, 500 — ошибка
сервера/сохранения. Ответ: `{ "error": "код", "message": "описание" }`.
Дополнительно: 413 `payload_too_large`, 415 `unsupported_media_type`, 429
`rate_limited` с Retry-After. JSON/ввод: `invalid_json`, `invalid_payload`,
`invalid_content_length`, `invalid_scenario`, `invalid_run_configuration`;
операции: `invalid_advance`, `invalid_event`, `invalid_goal`, `invalid_fork`,
`invalid_compare`, `invalid_adopt`, `invalid_schedule`, `invalid_preview`,
`invalid_explain`. Конфликты: `revision_conflict`, `branch_conflict` (409).

`/schedule` заменяет будущие назначения целиком:
`{"entries":[{"step":3,"satellite_id":"S01","action":{"action":"idle"}}]}`.
Для задания: `{"action":"job","job_id":"JOB-0001"}`; для калибровки:
`{"action":"calibrate"}`. Пустой список возвращает всё планировщику.
`/preview` принимает `until_step` (не более 96 шагов вперёд), возвращает
`source_revision`, `telemetry`, `summary`; родительский запуск не изменяется.

### Резервирование и очистка

```text
python -m web.maintenance --database results/operator.sqlite3 --directory backups --keep-backups 14 --keep-runs 100
```

Команда сначала создаёт согласованный SQLite backup, затем оставляет 100 последних
завершённых запусков каждого владельца и все незавершённые. Родители сохранённых
ветвей также сохраняются. Без `--keep-runs` запуски не удаляются. Удаляются только
старые резервные копии `operator-*.sqlite3` в выбранном каталоге; перед очисткой
архива всегда создаётся новая копия. Файлы резервирования содержат данные сервиса.
Для ежедневного запуска есть `deploy/hack-planner-backup.timer`; Windows Task
Scheduler может запускать ту же команду с абсолютными путями (инструкция в deploy).

Для отдельной копии: `python -m web.app --backup backups/manual.sqlite3`.
Имя не должно существовать или совпадать с рабочей БД. Для восстановления остановите
сервис, сохраните текущую БД вместе с её WAL/SHM, затем используйте файл backup как
новую базу через `--database`. Не подменяйте базу работающего процесса.

## Форматы

### События

Пакетный файл имеет `schema_version: "cosmo-B-events-1.0"`,
`base_scenario` и массив `events`. Интерактивный runtime/API принимает один
объект без оболочки. Поддерживаются:

- `add_jobs`: поля `id`, `at_step`, `type`, `jobs`;
- `satellite_outage`: поля `id`, `at_step`, `type`, `satellite_ids`, `end_step`;
- `close_downlink`: те же поля интервала, но закрываются только окна downlink.

Интервалы имеют вид `[at_step, end_step)`. ID события должен быть новым,
сообщение принимается атомарно только на текущем незавершённом шаге. Полный
пример находится в `examples/events_demo.json` и относится к P02.

### Результат

Экспорт `cosmo-B-ops-result-1.0` содержит:

- `initial_scenario` и его hash;
- `events` в порядке фактического получения;
- `commands` только для выполненных шагов;
- `steps_executed`, `run_metadata`, `summary` и подробный `trace`;
- для runtime дополнительно `history`, `state_digest` и версию runtime schema.

`summary` включает выполненные/просроченные и критические задания, выручку,
отклонённые команды, состояния ниже резерва/критического SOC, brownout,
минимальный и конечный SOC, а также работу в незавершённых заданиях. `trace`
различает намеренный `idle`, принятую операцию и конкретную причину отклонения.

## Replay

Replay не запускает планировщик: он повторно применяет сохранённые события и
команды к исходному сценарию и пересчитывает модельный учёт.

```text
python model/operations.py --result results/demo-result.json --output replays/demo-replay.json
```

Для корректного результата `summary` и `trace` исходной выгрузки и replay
совпадают точно. Допускается также раздельный ввод сценария, events и commands;
пример приведён в `examples/README.md`.

## Эксперименты

Пакетное сравнение summary двух алгоритмов:

```text
python -m planner.cli --scenario data/P01_intro.json --compare --goal revenue --output results/p01-comparison.json
```

Расширенный анализ доставляет каждое событие runtime только на его `at_step` и
добавляет счётчики причин, потерь, незавершённые задания, ресурсные индикаторы,
время выполнения и delta `strategic - baseline`:

```text
python -m planner.analysis --scenario data/P03_energy.json --goal revenue --output results/p03-analysis.json
python -m planner.analysis --scenario data/P02_shift.json --events examples/events_demo.json --goal priority --output results/p02-events-analysis.json
```

Поле времени является диагностическим и зависит от машины; план, summary и
trace детерминированы.

## Ограничения

- Лимит запроса: 8 MiB JSON, 6 MiB на custom scenario.
- SQLite хранит полные JSON-снимки с trace; большие архивы требуют места на диске,
  а восстановление через replay занимает время. Для обслуживания доступны
  `python -m web.app --database results/operator.sqlite3 --backup backups/operator.sqlite3`
  и `--prune-runs N`.
- Изменения сериализуются; нет фоновой очереди, WebSocket/SSE и распределённых
  вычислений. Долгие запросы могут упереться в таймаут клиента или reverse proxy.
- CLI ограничивает API до 120 запросов в минуту на peer IP (`--rate-limit`, 0 отключает).
  За reverse proxy общий peer IP принадлежит прокси, поэтому индивидуальный лимит
  клиентов следует устанавливать в Nginx. X-Forwarded-For не принимается на доверии.
- Ограничения числа сессий, MFA/SSO, восстановление пароля через почту и
  межоператорский sharing не добавлялись. Учётные записи меняются через CLI.
- TLS завершает reverse proxy. CORS включается настройкой сервера, `/api/v1`
  доступен всегда. HTTP-сервер стандартной библиотеки не заменяет полноценную
  production-платформу; нагрузочное тестирование и эксплуатационные меры остаются.
- Делайте резервные копии SQLite через backup API либо при остановленном сервисе;
  при WAL нельзя копировать только основной файл работающей базы.
- Не рассчитываются орбиты и радиоканалы: окна, солнечная мощность и тепловые
  условия уже заданы входными рядами.
- Strategic является детерминированной эвристикой rolling horizon, а не
  доказательством глобального оптимума.
- `results/`, `replays/`, кэши, `.env` и IDE-файлы исключены из git.

## Разработка и тесты

Проверка новых операторских инструментов в настоящем браузере:

```text
npm install --no-save playwright jsdom
npx playwright install chromium
node scripts/browser_smoke.cjs
node scripts/ui_smoke.cjs
```

На Windows можно использовать уже установленный Edge:
`$env:PLAYWRIGHT_CHANNEL='msedge'; node scripts/browser_smoke.cjs`.
Скрипты запускают отдельный сервер и временную базу. Browser smoke проверяет
назначения/перенос/прогноз, выполнение, пагинацию журнала, мультиграфики,
диапазон шагов, локальные шрифты и обе темы на десктопе/мобильной ширине.
Никакие данные основной локальной базы при проверке не используются.

Установка зависимостей не требуется. `pyproject.toml` фиксирует Python 3.10+ и
пустой список runtime dependencies. Проверка из чистого checkout:

```text
python -m compileall -q model planner web scripts tests
python -m unittest discover -s tests -v
python -m planner.cli --scenario data/P01_intro.json --planner strategic --goal priority --output results/smoke.json
```

GitHub Actions выполняет эти проверки на чистом `ubuntu-latest` для Python 3.10
и 3.12 без секретов.


Дополнительная DOM-проверка интерфейса с настоящим HTTP API (не проверяет
визуальную отрисовку браузера) использует необязательную dev-зависимость jsdom:

```text
npm install --prefix /tmp/cosmo-ui-test jsdom@26 --no-audit --no-fund
NODE_PATH=/tmp/cosmo-ui-test/node_modules node scripts/ui_smoke.cjs
```

Скрипт сам создаёт временную SQLite-базу и тестовую учётную запись, проверяет
upload, compare/adopt, timeline/explain, график аппарата, открытие сохранённых
запусков и пагинацию, затем останавливает тестовый сервер.
